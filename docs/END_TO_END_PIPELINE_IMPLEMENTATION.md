# Milestone 5A — deterministic end-to-end pipeline

## Objective and dependency graph

`TAIOSPipeline` is a narrow coordinator for the existing deterministic
components. It adds no decision thresholds or action-selection rules.

The actual dependency graph is:

```text
EventManager.validate(event)
  -> runtime_observation(event)
  -> synchronize observable production state / operating mode
  -> TrustAgent.assess(observation, persistent entity trust)
  -> RiskAgent.assess(observation, current trust)
  -> AuthorizationEngine.assess(observation)
  -> build_decision_context(..., current IndustrialState)
  -> AutonomousAuthorityEngine.assess(base context)
  -> build_decision_context(..., authority, current IndustrialState)
  -> PlanningAgent.plan(context)
  -> DecisionAgent.decide(context, plan)
  -> GovernanceAgent.review(context, plan, proposal)
  -> ExecutionAgent.execute(context, plan, proposal, governance, state)
  -> next episode state
```

Trust is stateful per source entity. Risk is evaluated from the current
observation and current trust assessment and is not retained as hidden episode
state.

## API and result contracts

`TAIOSPipeline.process_event(event, state) -> PipelineResult` validates and
processes one event. `TAIOSPipeline.run_episode(events, initial_state=None,
scenario_reference=None, seed=None) -> EpisodeResult` resets run-local trust
and execution state, then processes the ordered events sequentially.

`PipelineResult` contains the safe observable input, trust and risk
assessments, authorization and authority assessments, final DecisionContext,
PlanningResult, ProposedDecision, GovernanceDecision, ExecutionResult,
execution input/output states, regime-transition flag, component references,
pipeline version, and deterministic pipeline fingerprint. Its constructor
validates the complete context/plan/proposal/governance/execution chain.

`EpisodeResult` contains the scenario/experiment reference, audit-only
scenario ID and seed, ordered PipelineResults, initial/final state references,
structural proposal/governance/execution counts, and deterministic episode
fingerprint.

## State, trust, and regime continuity

The prior result's `state_after` is cloned and passed as the next event's input.
Successful execution uses its resulting state. Pending, rejected, stale, and
unsupported outcomes carry the unchanged state. PENDING_APPROVAL is recorded
and does not stop a simulated episode because no human approval workflow
exists.

Before inference, the runner applies only the production-state and
operating-mode values already present in the allowlisted runtime observation to
a clone of current episode state. This replays the deterministic environmental
regime generated by Day 1; ExecutionAgent does not create regime transitions.
S5 changes NORMAL to HIGH_OUTPUT at event 6 through this mechanism.

One TrustAgent instance persists for an episode. Entity-local observation
numbers increase in delivery order, so `previous_composite_trust`,
`composite_trust`, and trust-state versions form a continuous trajectory. Each
new episode starts a clean trust model. No risk history is invented.

## Failure, transactionality, and idempotency

Invalid event, observable projection, trust, risk, authorization, context,
authority, planning, decision, governance, and execution failures raise
`PipelineProcessingError` containing a deterministic `PipelineFailure` with
the failed stage, exception type, reason, event reference when available,
unchanged input-state reference, and pipeline version. Expected non-execution
is an ordinary PipelineResult and is not a pipeline failure.

Inference operates on cloned IndustrialState values. Before a component
failure is surfaced, TrustAgent state, entity counters, and the ExecutionAgent
ledger are restored to their pre-event checkpoints. No partial plant mutation
or partially consumed inference state remains.

Replaying a completed event with the same event identity/content and its
resulting state reuses the exact prior inference artifacts and calls the same
ExecutionAgent. The underlying ledger returns ALREADY_EXECUTED; the pipeline
does not implement a second execution path.

## Trace and fingerprints

The diagnostic trace groups existing structured outputs as what happened,
what TAIOS knew, what it considered, what it proposed, what governance did,
what execution did, and the component-provided reasons. No generated-language
explanation is added.

Pipeline fingerprints bind the safe event projection, ordered component
references, input/before/after state references, and pipeline version. Episode
fingerprints bind ordered pipeline fingerprints, scenario/experiment
reference, seed, initial/final state references, and version. Wall-clock time,
ground truth, expected action, scenario phase, causal tags, synthetic scores,
and audit identifiers are excluded from inference fingerprints. Reordering
events changes the episode fingerprint.

## Observed seed-42 behavior

S1 produced four ALLOW/APPROVED/SUCCEEDED events and six
REQUEST_APPROVAL/APPROVAL_REQUIRED/PENDING_APPROVAL events. Pending events did
not mutate state or stop the episode.

S2 produced five successful ALLOW executions followed by five pending review
outcomes. State version reached 5 at event 5 and remained 5 through events
6–10. PLC-07 trust persisted across all ten observations: composite trust rose
from the 0.8 prior to 0.8018230957031248 after event 5, then fell continuously
to 0.7805872941652932 after event 10 as negative behavior evidence arrived.

S3 produced ten REQUEST_APPROVAL/APPROVAL_REQUIRED/PENDING_APPROVAL outcomes,
zero mutations, and no fabricated `write_register 999` semantics. The review
burden remains 10/10 events because authorization and operational semantics are
unresolved.

S4 produced ten REQUEST_APPROVAL/APPROVAL_REQUIRED/PENDING_APPROVAL outcomes
and zero mutations. Existing evidence components remain separate; the pipeline
does not collapse them into a new attack threshold.

S5 produced ten ALLOW/APPROVED/SUCCEEDED results. Events 1–5 ran under NORMAL.
Event 6 applied the existing HIGH_OUTPUT transition, moving the episode state
from version 5 to 6 before execution and from 6 to 7 after applying 85 under
`[60,95]`. Event 7 requested 85 again and correctly remained at version 7 as a
successful no-op. Events 8–10 ended at versions 8, 9, and 10. No stale-state
result occurred.

S6 produced one successful ALLOW and nine pending-review outcomes. Current
agents do not aggregate cross-source activity or claim coordinated-attack
detection; the pipeline preserves that limitation.

Across S1–S6 and seeds 42, 123, 456, 789, and 2026, the 300-event structural
distribution was 93 ALLOW proposals and 207 REQUEST_APPROVAL proposals; 93
APPROVED and 207 APPROVAL_REQUIRED governance outcomes; and 93 SUCCEEDED and
207 PENDING_APPROVAL execution outcomes. These are integration measurements,
not accuracy or security-effectiveness metrics.

## Leakage boundary, limitations, and evaluation readiness

Only `runtime_observation` enters inference. Integration tests alter ground
truth, expected action, scenario ID, synthetic score keys, causal/transition
keys, event ID, and sequence audit metadata without changing the decision
context, execution result, or pipeline fingerprint. Scenario ID and seed remain
episode audit metadata only. Evaluation labels never appear in the diagnostic
inference trace.

The implementation remains a simulated, in-process runner. The execution
ledger and trust state are not durable or distributed. There is no external
approval service, device adapter, monitoring platform, BLOCK/ISOLATE physical
semantics, adaptation, drift learning, memory learning, threat detector, ML,
baseline, ablation, statistical testing, LLM, or LangGraph integration.

The deterministic full-chain artifacts, state/trust trajectories, leakage
boundary, structural summaries, and reproducibility output are ready to be
consumed by a separate formal evaluator. Existing trust, risk, authorization,
authority, planning, decision, governance, execution, scenario, and policy
logic was not retuned.
